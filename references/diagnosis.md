# 判断标准：问题在哪一层

核心手法是**把变量分开**，而不是猜。灯带系统只有四个可能出问题的层，每层都有对应的"一句话判据"。

```
第 0 层  通路      电到位了吗？地共了吗？数据线接对了吗？
第 1 层  数据完整性 整帧数据有没有被灯珠全部收到？
第 2 层  编码      收到的字节有没有被解释成正确的颜色？
第 3 层  渲染      我们喂给灯珠的画面本身对不对？
第 4 层  交互      人能不能控制它、设置有没有留下？
```

## 先做的一件事：确认"芯片在跑"

板载小灯 / 串口日志在动 = 程序在跑。**此时灯带全黑绝不等于程序有问题**，直接跳到第 0 层。

反例：如果板载灯在闪但其实是无复位循环，日志会每几秒从头重来。看到**同一段开机日志反复出现**就是复位循环，不是"在跑"。

---

## 第 0 层：通路

| 判据 | 结论 |
| --- | --- |
| 灯带 5V 和 GND 之间量不到 5V | 供电没到位（线 / 电源 / 焊点） |
| 有 5V，但开发板和灯带不是同一个地 | **共地缺失**——数据线没有参考电平，行为完全随机 |
| 有 5V、共地正常、DIN 接着数据脚 | 进第 1 层 |

**"USB 一拔灯效就停"** 是这一层的典型症状：灯带在吃开发板 USB 那点电，独立供电后消失。

**灯带丝印要确认**：焊点旁印 `+5V` 才对。印 `+12V` 的灯带用 5V 永远不亮。

---

## 第 1 层：数据完整性

特征是"**亮了一部分**"，不是全黑也不是全亮。

| 判据 | 结论 |
| --- | --- |
| 亮的颗数随灯珠总数变化 | 数据长度 / 缓冲问题（降速、加帧头、整帧直发） |
| 亮几颗**完全固定** | 第 N+1 颗或它附近的焊接有问题 |
| 用"单颗定位"逐颗点，从第 N 颗起不动 | 硬件断点就是第 N+1 颗 |

处置优先级：**降速 → 加帧头缓冲 → 改用整帧直发（不要分包）**。这三个都是运行时命令，改完立刻看效果，不用重新编译。

---

## 第 2 层：编码

灯"亮对了数量"，但颜色不对。

| 判据 | 结论 |
| --- | --- |
| **整条**都错（发红出绿） | 位序配置（GRB / RGB） |
| **只有第一颗**错 | 首颗采样点被前导电平污染 → 开"首颗启动缓冲"+ 调帧头 |
| 只有**某几颗**错 | 那几颗灯珠坏了 |
| 第一颗偏黄 / 偏绿 | 同上，首颗的红色分量被前一帧的尾巴吃掉 |

用"参考灯"（前 4 颗固定红绿蓝白）判：如果这 4 颗的顺序和颜色都对，第 2 层没问题。

---

## 第 3 层：渲染 —— 怎么区分"电路问题"和"算法问题"

这是最容易误判的一层。**唯一的可靠办法是让画面停下来。**

### 三步分离法

1. **跑"斑马纹"**（画面完全静止，不做任何动画）十分钟。
   - 不闪 → 传输和供电都没问题，**是动画本身**（第 3 层）
   - 还闪 → 回第 0 / 第 1 层
2. **跑单色常亮**（同一帧反复输出）。
   - 不闪 → 同上，动画的问题
   - 还闪 → 传输 / 供电
3. **看闪烁的位置分布**：

| 闪烁位置 | 结论 |
| --- | --- |
| 固定在开头 1~2 颗 | 前导 / 采样点 → 帧头缓冲、首颗启动缓冲 |
| 固定在某一段 | 那一段的供电压降或焊接 |
| 中间随机几颗不定时亮起 | **帧内有缝隙**，被灯珠当成锁存信号 → 改整帧直发 |
| 全条随机、无规律 | 电源纹波 / 数据电平不足（3.3V 临界） |

### 动画侧的真实原因

如果确认是第 3 层，通常是这几种：

- **每帧写入的长度不一致**：有空隙就被灯珠当锁存，画面撕裂
- **帧率抖动**：某些帧特别慢，人眼就看成一跳
- **颜色过渡步进太大**：不是真的频闪，是量化跳变被眼睛读成闪烁——把插值步长调小、周期放慢就顺了

### 用"心跳"读渲染健康度

固件每 5 秒打一行心跳，含三项关键指标：

- **帧率**：稳定才好。忽高忽低说明有卡顿
- **最慢一帧**：明显大于平均值 = 有周期性卡顿
- **这一帧约 XXX 毫安**：既能验证亮度设置是否真的生效，也能验证有没有超电源预算

---

## 第 4 层：交互

| 现象 | 结论 |
| --- | --- |
| 改了亮度没反应 | 看心跳里的电流有没有跟着变——没变就是命令没到板子 |
| 断电后回到默认 | 该参数没写 NVS |
| 手机搜不到热点 | 热点名被改过；或手机自动切回了蜂窝 |
| 网页状态不动 | 控制台的解析规则和固件回话格式对不上了 |

---

## 汇报给用户的话术

先说**结论**（是哪一层），再说**要看什么才能确认**，最后给**一个动作**。不要一次给三个可能。

用户已经明确确认过的事（比如"线是焊的，反复查过了"），当成事实。要拿新证据就换个**没用过的**验证方式，不要让人重做同一件事。
